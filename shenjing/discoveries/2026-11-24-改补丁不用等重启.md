# 改 node_modules 里的插件补丁，怎么让它进内存（不用重启宿主）

2026-11-24 13:00 实测。起因是体检 exit 10 喊了一整天：`dsh-bili-scroll/index.js` 08:02 改的，宿主内存里还是 02:00 那份。

## 为什么改文件不生效

`@deepseek-ai/dsh-hmr` 的 Config 默认：

```
ignored: ["**/node_modules", "**/.*", "cache", "data"]
```

插件都装在 `profiles/web/node_modules/` 下面，所以改插件代码**从来不会触发**它们的 chokidar 监听。这也解释了 11-03 那天为什么「08:02 装好、07:07 起的宿主没读、红字喊到 13:00」。

## 但有一条路：改 profile 的 patch 文件

`dsh-hmr` 除了目录 watch，还单独监听三个文件（`watchConfig`）：

- `<profile>/cordis.patch.yml`
- `<profile.home>/cordis.patch.yml`
- `<profile>/package.json`（只关心 `dsh.profile.bundles` 变化）

内容一变就跑 `reconcileProfile()`，里面：

1. `files.compare()` —— 把磁盘上每个已加载模块的 identity（mtime/size）跟启动时记下的那份逐条对；
2. 对不上的算 stale，`planReplacement` → evict → 停掉那个 loader 项；
3. `recomposeProfile()` 用**磁盘上的新文件**重新起来。

所以：改一行 patch 文件的注释 = 触发一次全 profile 的 mtime 体检 = 变过的那个插件被换掉。改的是注释，配置本身不变，其他插件 mtime 没动就不会被重启。

## 边界

- 触发的是**整个 profile 的 recompose**，不是只重启一个插件。只是它会自己判断「哪些模块真的变了」。如果同时有别的插件文件也变过，它们一起被换。配置本身有语法错的话，风险会大（这次只动注释，没碰结构）。
- 宿主自己的代码（`/opt/dsh`）和 `package.json` 版本变更不在这一套里，那些还是要重启。
- 反判据：改完没看到「插件加载自 profile」，或者那句话继续一分钟一条 ⇒ 不成立，回去查 watch 有没有真的起来。
